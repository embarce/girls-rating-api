## 分页接口与缓存设计评审（未改代码，仅输出结论）

- 分页：`Order("create_time DESC")` 无 tiebreaker + `create_time` 秒级 → 深翻页重复/漏（需加 `id DESC` + 复合索引）；`page` 无上限且直接进缓存 key，可被用来批量造 key + 制造慢查询；`pageSize` 非法值静默降级为 10。
- 一致性问题：`rating` 在 `/api/random` 走 `CAST(rating AS UNSIGNED)`（四舍五入 4.7→5），`/api/cosplay` 走 `int(item.Rating)`（截断 4.7→4）。
- 缓存：read-through 回填与上传 `SCAN`+`DEL` 之间存在竞态（旧结果被写回，脏数据存活到 TTL）；无 singleflight、无 TTL 抖动；`pkg/redis` 未配超时（默认 3s×3 retries，Redis 抖动会拖慢 `/api/cosplay`）；`PAGE_CACHE_TTL_SECONDS=0` 被默认值吞掉无法关闭缓存；key 无环境前缀。
- 建议方案：版本号 key（`...:ver` + `INCR`）替代 SCAN 全量删除，可一次性解决竞态 + key 格式耦合；配套 singleflight、`ORDER BY create_time DESC, id DESC`、Redis 超时压到 200ms。

- 待决策：前端形态（小程序不支持 Turnstile）、refresh 存 Cookie 还是 localStorage、是否邮箱验证、旧接口是否保留、大陆用户占比（决定 cn 域名）、后续业务（收藏/评分）。

## 决策变更 2：会话管理中移到 Redis 白名单（v0.3，用户提出，成立）

- 用户观点：JWT 只是载体，登录态用 Redis 管，删缓存即下线。**判断正确**，采纳。
- 澄清的语义差别：「删除即登出」= **白名单**（登录写 `sess:{uid}:{jti}`，鉴权 EXISTS，删除失效）；黑名单是「添加才踢、删除反而恢复」。
- 关键前提：**JWT 必须带 `jti`**，否则同用户多端登录无法区分、无法单独登出。
- key 设计：`{env}:auth:sess:{user_id}:{jti}` → `"1"`，TTL 与 JWT exp 严格一致（写入时算 exp-now）。key 里带 user_id 使**封号时可用前缀 SCAN 批量删，无需额外索引 Set**（这是比 v0.1 省掉整张表的关键）。
- 故障策略：**fail-open**（Redis 报错则放行，退化为纯 JWT；miss 则 401）。理由：签名已验证，fail-close 会让 Redis 抖动=全站掉线。
- 应急开关 `SESSION_ENABLED`，false 即退回 v0.2 纯 JWT 行为，无需改代码。
- 仍不做：refresh 轮转、MySQL 会话表、登录日志表、滑动续期、渐进式验证码。
- 接口 4 个：register / login / logout（幂等）/ GET user。

## 新增 docs/design/task-system.md（异步 AI 图片任务体系，v0.1）

- 核心决策：**队列就用 MySQL `image_tasks` 表**，不用 Redis List/Stream。理由：AI 任务耗时几十秒以上，1s 轮询延迟被上游耗时淹没；而「Redis 排队 + MySQL 记状态」的双写一致性是最大 bug 源；`FOR UPDATE SKIP LOCKED`（MySQL 8）提供原子抢占。Redis 只用于每日配额计数。
- 表 `image_tasks`：task_no（16字节随机hex，对外暴露，不用自增 id 防遍历）、status(0-4)、priority、params JSON、result_urls JSON、progress、stage、attempts/max_attempts、worker_id、lease_expires_at、next_run_at（退避）、cancel_requested、idempotency_key（唯一索引 user_id+key 防连点）。5 个索引分别服务抢单/列表/僵尸回收。
- **两个最容易漏的点已写进文档**：①租约 + 僵尸回收（worker 被 kill -9 后任务不能永远卡 running）；②所有状态更新带 `AND worker_id=?` 防 ABA（被回收后旧 worker 的迟到回调覆盖新状态）。
- worker：默认与 API 同进程（`WORKER_ENABLED`），goroutine 池并发（默认 2），1s 轮询，SKIP LOCKED 保证多副本安全；优雅停机时主动释放任务而非等租约过期。Provider 接口 `Run(ctx, req, onProgress)`，先写 `mock` 实现（无凭证可跑通全链路）。
- 接口 5 个：POST /tasks(202) / GET /tasks/:taskNo / GET /tasks / POST /tasks/:taskNo/cancel / GET /tasks/quota。状态出参用字符串（pending/running/succeeded/failed/canceled），DB 存 TINYINT；服务端下发 `pollAfterMs` 控制轮询节奏。
- 列表排序用 `ORDER BY id DESC`（自增主键天然唯一，避开 /api/cosplay 的同秒排序问题）。
- 配额：每日 20 次（Redis）+ 进行中 2 个（DB count）；失败返还一次，取消不返还。
